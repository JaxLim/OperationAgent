# M5.2 基准：选择性检索（2026-11-12）

命令：`pnpm bench:agent`（新增 `retrieval` 一节）。结果写入 `artifacts/bench/<平台>/agent.json`（不入库）。

- 环境：Windows 11 x64，Node 24.22.1，`m5-selective-retrieval` 分支。全部经真实 Tool Router 与 Read Adapter 子进程，本机运行，不调用模型。
- 测的是**两条路径各自的代价**，不是模型会选哪条路径。模型是否真的“先搜索、再按行读”，要在真实 API 上观察（尚未验证）。

## 场景

一个 40 个文件的项目（每个约 16 KiB、400 行，共 675,207 字节），其中只有一个文件第 201 行有要找的定义。

| 路径 | 工具调用 | 返回给模型的字节 | 耗时 |
|---|---:|---:|---:|
| 读全部：`list_directory` + 每个文件 `read_file`（每批 4 个并行） | 41 | 675,207 | 946 ms |
| 先搜后读：`search_text` + `read_file` 读匹配处前后 20 行 | 2 | 931 | 161 ms |

先搜后读返回的字节是读全部的 **0.14%**，调用次数从 41 降到 2，耗时约为六分之一。返回给模型的字节会进入会话、在之后每一轮重复发送（见 M5.1 基准），所以节省会随轮数累积。

| 单次操作（同一项目，10 次） | p50 | p95 |
|---|---:|---:|
| `search_text` 搜索整个项目（40 个文件全部扫描） | 89 ms | 95 ms |
| `find_files` 按名称查找整个项目 | 77 ms | 84 ms |
| `read_file` 4 KiB（对照，来自同一次运行） | 75 ms | 80 ms |

一次整项目搜索的耗时与一次读文件相当：子进程启动（约 70 ms）占了大头，扫描 660 KiB 只多花十几毫秒。

## 结论

1. **少读比快读重要**，M5.1 的判断在这里得到实测：同样找到一处定义，字节数相差约 700 倍，耗时相差约 6 倍。
2. 搜索本身不贵，所以工具说明和系统提示都引导模型“先找后读”；`read_file` 的整文件截断提示也会告诉模型可以按行继续读。
3. 每次调用固定约 70 ms 的子进程成本依然存在，是 SEC-08 隔离的代价。下一步若要再省时间，方向是让模型在一轮里并行发出多个独立调用（系统提示已要求），而不是去掉隔离。

## 未验证

- 真实模型是否按引导先搜索、按行读取，以及由此带来的真实 Token 与费用节省：需要真实 API。
- 数据只来自一台 Windows x64 机器；其他平台没有 Read Gate，这些工具在那里返回 `READ_ADAPTER_UNAVAILABLE`。
