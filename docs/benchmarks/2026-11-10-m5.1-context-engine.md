# M5.1 基准：上下文引擎与度量（2026-11-10）

命令：`pnpm bench:agent`（先 `tsc -b`，再运行 `scripts/bench-agent.ts`）。结果写入 `artifacts/bench/<平台>/agent.json`（不入库）；本文件记录一次本机运行的结果和由它得出的结论。

- 环境：Windows 11 x64，Node 24.22.1，源码 `m5-context-engine` 分支，本机假 Messages API（真实 HTTP、真实 SSE、真实 SDK 流解析）。
- **实测**的部分是控制面自身的开销、只读工具调用的开销和一次脚本化任务；耗时随机器变化，请求大小和次数是确定的。
- **成本模型不是实测**：它按供应商公布的缓存与计价规则做算术，用来比较上下文策略。真实 API 上的行为和费用尚未验证（需要密钥与同意，见 ADR-PLAT-001 §8）。

## 1. 实测结果

| 项目 | 结果 | 含义 |
|---|---|---|
| 网关每回合开销（200 回合，假服务立即回复） | p50 0.8 ms，p95 1.4 ms，最大 4.1 ms（另一次运行 p50 2.6 ms） | SDK、受控 fetch、流解析与回环 HTTP 合计约 1～3 ms，相对模型延迟可以忽略 |
| 首段内容延迟的自身开销 | p50 1 ms | 同上 |
| 200 回合新建连接数 | 0 | 每回合新建 SDK 客户端并不重建连接，平台 fetch 复用了 keep-alive 连接 |
| `read_file` 4 KiB | p50 75 ms，p95 97 ms | 一次只读工具调用的固定成本 |
| `read_file` 256 KiB | p50 78 ms，p95 108 ms | 与 4 KiB 几乎相同：成本在子进程，不在读取 |
| `list_directory`（120 项，深度 2） | p50 99 ms，p95 124 ms | |
| 16 次并发 `read_file`（并发上限 4） | 352 ms | 约 4 批 × 88 ms |
| 脚本化任务：24 轮，每轮读 2 个 16 KiB 文件 | 完成，48/48 次工具调用成功，墙钟 3.1 s，工具耗时合计 4.7 s | 真实 Worker 运行时、Task Runner、Read Adapter |
| 同一任务的请求体 | 首个 2.5 KB，最后一个 781 KB，25 个请求合计 9.8 MB | 每轮重发全部历史，上传量随轮数平方增长 |
| 前缀被改写的块数 | 0 | 每个请求都是上一个请求的逐字节延伸（只追加） |

## 2. 由实测得出的结论

1. **控制面不是瓶颈。** 每回合约 1～3 ms，连接被复用；不需要为“每回合一个客户端”做优化。
2. **只读工具的成本是固定的 75～100 ms，与文件大小无关。** 这是短命子进程的启动成本，是 SEC-08 隔离的代价，不应通过常驻进程去掉。减少调用次数比加快单次调用更有效：这直接支持 M5.2（一次调用按行范围读取、搜索、按名称查找），而不是优化子进程。
3. **上传量是下一个瓶颈。** 24 轮任务合计上传 9.8 MB；服务端压缩减少的是模型看到的内容和计费 Token，并不减少客户端重发的字节。压缩后在客户端丢弃摘要之前的消息可以解决，但需要先在真实 API 上确认，本切片没有做。
4. **只追加成立。** 这是思考块绑定与提示缓存的前提，已作为单元测试固定（`tests/m2/context-engine.test.ts`）。

## 3. 成本模型（算术，不是实测）

假设：缓存读取价格为基础输入价的 0.05 倍（Opus 5.5）或 0.1 倍（Sonnet 5.5、Haiku 5.5），5 分钟缓存写入 1.25 倍；Haiku 5.5 在提示超过 100K Token 时整个请求按 5 倍计价；每回合的提示是到那时为止的全部会话，前缀未变的部分按缓存读取、新增部分按缓存写入；一次摘要再读一遍提示并输出约 2K Token，随后会话从摘要重新开始；清理旧工具结果会使第一个被清理结果之后的全部内容重新写入缓存。数值单位为“等价的基础输入 Token”，只比较输入侧。

三种策略：不管理；**生产策略**（只做服务端摘要：Opus / Sonnet 在 300K、Haiku 在 80K）；清理方案（保留最近 16 次工具结果即一整轮，Opus / Sonnet 在 350K 清理、700K 摘要兜底）。

| 场景 | 模型 | 不管理 | 生产策略（摘要次数） | 清理方案（清理次数） |
|---|---|---:|---:|---:|
| 短：8 轮 × 2 次 × 4K | 三种模型 | 84K～93K | 相同（0） | 相同（0） |
| 中：40 轮 × 2 次 × 8K | Sonnet | 2,022K | 1,363K（2） | 1,795K（2） |
| | Opus | 1,412K | 1,076K（2） | 1,449K（2） |
| | Haiku | 9,511K | 907K（7） | 939K（0，另摘要 6 次） |
| 长：40 轮 × 4 次 × 8K | Sonnet | 3,988K，**第 32 轮起超出窗口** | 2,078K（3） | 2,892K（5） |
| | Opus | 2,785K，超出窗口 | 1,791K（3） | 2,551K（5） |
| | Haiku | 19,406K，超出窗口 | 1,423K（13） | 1,423K（摘要 13 次） |
| 重：40 轮 × 4 次 × 16K | Sonnet | 7,919K，**第 17 轮起超出窗口** | 3,226K（7） | 7,799K（17） |
| | Opus | 5,530K，超出窗口 | 2,952K（7） | **7,530K（17）** |
| | Haiku | 39,266K，超出窗口 | 2,143K（19） | 2,143K（摘要 19 次） |
| 宽：40 轮 × 12 次 × 4K | Sonnet | 5,954K，超出窗口 | 2,704K（5） | 3,079K（6） |
| | Opus | 4,158K，超出窗口 | 2,418K（5） | 2,797K（6） |
| | Haiku | 29,256K，超出窗口 | 1,682K（19） | 3,120K（37） |

“超出窗口”的任务在那一轮会失败，其后的成本没有可比性。

### 由模型得出的决定

- **只启用摘要，不启用工具结果清理。** 为了不清掉模型还没看到的结果，必须保留一整轮工具调用（每轮最多 16 次）；每次清理都要把这段尾部重新写入缓存。在全部场景中清理方案都不比摘要便宜，重读取场景下（Opus，7,530K 对 5,530K）甚至比不管理更贵。最初拟定的“先清理、后摘要”策略因此被放弃，ADR-PLAT-001 D1 已同步修订。
- **短任务完全不受影响**：未到阈值时请求除多一个参数外没有任何变化。
- **Haiku 5.5 的收益主要来自避开 100K 以上的 5 倍计价**，所以它的阈值定在 80K。
- **读入的新内容本身才是成本的大头**：每轮新读的内容都要按 1.25 倍写入一次缓存，任何上下文策略都省不掉。少读才是根本，这再次指向 M5.2。

`tests/m2/context-engine.test.ts` 把上述结论固定为断言：生产策略在每个场景、每个模型上都不超出窗口、不比清理方案贵、不比不管理贵，且阈值以下与不管理完全一致。策略或模型任一改动而结论不再成立时测试失败。
